### 如何本機預覽

從 **repository 根目錄** 啟動靜態伺服器，不要直接雙擊 `file://` HTML：

```bash
python3 -m http.server 8000
```

- 放鬆方案：`http://localhost:8000/pilot/?product=relax`
- 重要場合方案：`http://localhost:8000/pilot/?product=stage`

兩種方案都有可實際操作的五題問卷、規則式個人化成果、報告預覽、售價展示、興趣 CTA。商品選擇互不污染答案。

手機 rPPG 的讀取**並非必要條件**，且必須使用者主動勾選同意、按下讀取，才動態載入既有 LINE + Supabase 的唯讀掃描 API。首次登入需要回到測試頁再按一次。當資料無法讀取時，問卷和結果仍可正常使用。不跨產品持久保存掃描資料。

`pilot/products.js` 為可替換題目與規則，`pilot/index.html` 是獨立展示介面，不修改原 `engine/data/questions.json`、`linebot`、`intake`、正式 LINE 選單或正式資料表。

## 第一輪實驗設計

1. 在**同一類合格受眾**中，將兩個商品分別推出；不要直接把不同族群下的兩個付費率拿來當因果 A/B 結論。
2. 每個商品獨立追蹤 `landing_view`、`quiz_start`、`quiz_complete`、`scan_read_requested`、`scan_read_success`、`interest_click` 和真正付款成功事件 `payment_success`（最後者待上線後實作）。
3. 導入小規模受眾先測試手機相容性、問卷完成率、使用者對 NT$1,290 / NT$1,490 的接受度；願意點擊不等於願意付款。
4. 正式加上支付與獲客成本記錄後，再檢查每個產品的 **付費訂單 / 合格獨立訪客**、退款率、客服時間、扣除金流與行銷後的貢獻利潤。
5. 如果要估算「rPPG 帶來的增量」，應在同一商品、相似客群與同樣售價下，隨機比較 **可選 rPPG 引導** vs **純問卷引導**，而非比較兩個不同商品。

### 上線前阻擋條件

- **不合規宣稱**：rPPG 不用來判斷情緒、壓力程度、焦慮、疾病，也不宣稱練習必然降低心率。內容為一般生活練習，不是醫療或心理治療。
- **獨立同意**：正式娛樂／課程商品不可直接挪用保健品目的下的既有生理數據；須完成不同目的下的授權、保存及刪除策略。現階段只在明確同意時臨時唯讀顯示。
- **安全體驗**：緩和呼吸、不憋氣、不強迫調節；如感到不適立即停止。心理困擾、醫療狀況及療效諮詢須轉合適的專業人士。
- **LIFF**：確認 `/pilot/` 路徑在該 LIFF endpoint 設定允許範圍內；在 LINE iOS/Android 及外部瀏覽器測試登入、連結、相機及訊息權限。
- **金流與交付**：串接線上付款前必須實作伺服器端簽章驗證、付款狀態與內容授權；不要只在前端用按鈕解除鎖定。
- **行銷透明**：先標示測試價格與尚未收款，不得宣稱已有實測成功率或真實 AI 指導功能。

## 架構上的後續做法
